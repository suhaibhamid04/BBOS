# BBOS Open-Source Component Matrix

**Evidence date:** 2026-10-23. Each repository is pinned to a commit so the reviewed source and license can be reproduced. A later release requires a fresh license, dependency, vulnerability, and behavior review. Repository claims are treated as evidence of intent, not proof that a feature meets BBOS acceptance criteria.

## Decision vocabulary

- **INTEGRATE:** use the component behind a BBOS-owned interface after a security/dependency review.
- **ADAPT:** prototype or reuse focused portions/patterns; do not import the whole application.
- **REFERENCE:** study architecture or UX, with no runtime dependency planned.
- **DEFER:** credible, but unnecessary or operationally disproportionate for the MVP.
- **REJECT:** license, architecture, maturity, or fit is incompatible with this project.

## Required-candidate conclusions

### Should Postiz run as an isolated scheduler?

Only if BBOS later needs several social networks and the saved provider work exceeds the fixed operational and compliance cost. The boundary should be one-way and minimal: BBOS sends an approved publication version, destination, schedule, controlled media URL, caption, and idempotency key; Postiz returns state and platform IDs. It must not decide approvals, read BBOS bookings/finances, or own the canonical audit. Counsel must evaluate AGPL-3.0 obligations for the actual hosted/modification model.

For the Instagram/Facebook-only MVP, a direct adapter is smaller, easier to authorize, and avoids running Postgres, Redis, Temporal, and another application.

### Are Diffusion Studio components reusable?

Potentially. Its packages and composition model justify a time-boxed spike. The application uses SolidJS/Electron while BBOS uses React/Vite, so direct UI embedding is inappropriate. The spike should test whether selected runtime/encoder concepts can be wrapped without importing the desktop shell, whether browser preview matches FFmpeg output, and how modified MPL-covered files will be tracked and offered. If those tests fail, retain only learned concepts and the BBOS JSON schema.

### Is OpenReelio mature enough?

No for a production dependency at this stage. It is an early `0.1.x` desktop application with an architecture that does not fit BBOS's browser/server model. It is useful reference material for timeline interaction, local preview, captions, and FFmpeg/WASM boundaries. Reassess after stable releases, documented migrations, security practices, and evidence of production adoption.

| License | Candidates | Practical implication for BBOS | Required review/control |
|---|---|---|---|
| MIT/BSD/Apache-2.0 | Uppy, Konva, whisper.cpp, OpenReelio, PySceneDetect, MediaInfoLib, Sharp, OpenCV | Permissive commercial use subject to notices and license terms; Apache-2.0 includes express patent provisions and NOTICE handling where applicable. Dependencies/assets can have different terms. | Preserve notices, produce an SBOM, scan dependencies, record asset/model licenses. |
| MPL-2.0 | Diffusion Studio | File-level copyleft generally requires source availability for modified covered files when distributing them. Combining with separate BBOS files does not automatically relicense all BBOS code. | Counsel confirms deployment/distribution analysis; isolate covered files, track changes, retain notices, exclude protected branding. |
| LGPL-2.1-or-later | Default FFmpeg configuration | Dynamic/static linking and distribution choices affect relinking/source obligations. Enabling GPL components changes the effective license; nonfree configuration prevents redistribution. Codec patents remain separate. | Reproducible build manifest, legal review, source/notices and relinking path where required; prohibit `--enable-nonfree`; explicitly approve enabled libraries/codecs. |
| GPL-2.0/GPL-3.0 | LosslessCut, Olive; optional FFmpeg features | Strong copyleft can require corresponding source for a distributed combined/derivative work. Architecture and method of interaction matter. | Do not embed these apps in MVP; legal review before code reuse. |
| AGPL-3.0 | Postiz | Network interaction with a modified AGPL program can trigger an obligation to offer corresponding source to remote users. Running it as a separate service does not itself erase obligations. | Legal review of modifications, deployment, notices, source-offer process, and integration boundary. |
| Mixed MIT/restricted | Activepieces | Only specified community paths are MIT; enterprise directories are under a restricted commercial license. Transitive assets/connectors may differ. | File-level provenance review; do not import EE code; prefer no runtime dependency for MVP. |
| Custom source-available | react-video-editor/OpenVideo | Fails the requirement for verified OSI-approved licensing. | Reject. |

The [OSI license pages for MPL-2.0](https://opensource.org/license/MPL-2.0), [AGPL-3.0](https://opensource.org/license/AGPL-3.0), and [LGPL-2.1](https://opensource.org/license/LGPL-2.1), plus [FFmpeg's legal guidance](https://ffmpeg.org/legal.html), are starting points rather than legal advice.

## Security gate for every dependency

Before implementation, the owner must pin a release/commit and artifact hash, generate an SBOM, scan direct/transitive dependencies and container layers, verify provenance/signatures when provided, enumerate native codecs/protocols, run a license scan, define patch ownership and end-of-life handling, and pass hostile-file tests. A README feature becomes accepted only after a BBOS proof of concept passes the measurable tests in the roadmap and MVP specification.
